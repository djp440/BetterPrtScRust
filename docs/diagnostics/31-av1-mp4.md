# #31：AV1 MP4 收尾与小尺寸系统解码

更新时间：2026-10-31 20:02（UTC+8）。编码、封装和系统解码的自动检查已通过；用户启动最新构建后确认「验收已没有问题」。此前的 GUI 待验收状态解除，以用户确认作为人工验收证据；#31 由修复 PR 合并时关闭。

## 根因与修复

目标环境：Windows 10 19045，NVIDIA GeForce RTX 5070 Ti，驱动 621.01；同时装有 AMD 核显。

原实现的 AV1 自检能写入帧，但 Finalize 报 `0xC00D4A45`。实际 D3D11 适配器和 `IMFSinkWriterEx::GetTransformForStream` 的诊断确认：

- 使用 RTX 5070 Ti 和 `NVIDIA AV1 Encoder MFT`，不是误选 AMD 核显。
- 编码器输出类型和 MP4 sink 当前媒体类型都有 14 字节 `MF_MT_MPEG_SEQUENCE_HEADER`；单独重设同一份序列头不能修复问题。
- Windows 10 的 MPEG-4 sink 没有据此生成 AV1 sample description。在其他条件不变时，补全描述即可正常 Finalize。

生产代码在 AV1 收尾前，按系统自定义格式约定设置 `MF_MT_MPEG4_SAMPLE_DESCRIPTION`，包含 `stsd`、`av01`、`av1C` 和原始 sequence header OBU。profile、level、tier、位深和色度来自实际序列头；系统继续完成编码和音视频封装，不改写视频帧、不增加程序运行依赖。

首次补丁还有一个格式问题：将实际帧尺寸直接写入 av01。硬件编码器可以在同一个序列最大尺寸下输出较小帧，例如 256×256 的实际帧使用 1920×1088 的序列最大尺寸。AOM AV1 ISOBMFF §2.2.4 要求 av01 使用序列最大尺寸；若 render 宽高比不同，还需 `pasp` 补偿。修复后：

- av01 的宽高读取自序列头；实际尺寸超过最大尺寸时返回明确错误。
- tkhd 保持实际录制尺寸；pasp 的比例为 `render_width × max_height / (max_width × render_height)`，约分后写入。
- 增加独立 AV1 解析器校验，避免测试和生产解析器共享同一个错误。

规范入口：Microsoft「MPEG-4 File Sink」的 Sample Description Box；AOM「AV1 Codec ISO Media File Format Binding」的 AV1SampleEntry / AV1CodecConfigurationRecord。生产代码旁保留对应链接。

## 小尺寸缓冲区错误的后续定位

此前 384×256 在 Windows Source Reader 的基础软件视频处理路径中报 `0xC00D36B1`，而 1920×1088 对照通过。该现象不能据此判定文件损坏或显卡驱动有问题。

对相同的小尺寸文件，给 Source Reader 配置 D3D11 设备管理器、启用硬件转换和高级视频处理、关闭基础软件视频处理后，Windows 可成功返回帧。该路径首帧会报告 `MF_SOURCE_READERF_CURRENTMEDIATYPECHANGED`，测试必须刷新当前尺寸和行跨度。

进一步用实际画面比对发现，RGB 输出还需保留输入的像素比例，避免高级视频处理自动加黑边；GPU 二维缓冲区必须使用 `IMF2DBuffer::Lock2D` 返回的真实 pitch，不能套用媒体类型中可能方向相反的默认行跨度。这些均已修正，并以正负 pitch、带填充的行及故意错误的声明 stride 建立回归。

扩展解码辅助函数时，H.264 的 34×34 小画面曾被错误地按 48×48 对齐缓冲区报告。现在先按完整缓冲区布局读取，再裁去右侧和底部填充；原有小区域冒烟另增首帧画面对比，重跑通过。

因此，之前「小尺寸系统解码仍未解决」的结论已过时。各测试尺寸均通过 Windows 解码和画面比较；随后用户确认最新构建验收通过。自动检查和用户验收均针对本次目标环境，不扩展为所有播放器的兼容性结论。

FFmpeg / ffprobe 仅用于真机测试；独立解析器 `avif-parse` 复用现有 workspace 依赖并仅作 dev-dependency。默认工作区测试不操作真实桌面；真实硬件编码测试仍显式标记 ignored。

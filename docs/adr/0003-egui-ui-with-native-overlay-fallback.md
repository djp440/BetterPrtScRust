# 界面使用 egui，选区遮罩保留原生回退方案

选区遮罩、标注工具条、录屏控制条、设置和 OCR 结果窗口统一使用 egui（基于 winit + wgpu），这样一套界面代码以后可以跨平台，安装包也能控制在 15 MB 以内。没有选 Tauri，因为它的常驻内存会超过 30 MB；没有直接选原生 Win32 + Direct2D，因为界面代码无法跨平台。前提是先做原型，实测从按下热键到出现遮罩的延迟：如果超过 150 ms，选区遮罩改用原生绘制，其余界面仍用 egui，并把本 ADR 改为 accepted 或 superseded。

## 原型结论（#2，2026-10-24）

egui 选区遮罩的延迟本身达标，但无法同时满足“常驻内存 < 30 MB”。延迟达标的前提是把 wgpu 设备和遮罩窗口常驻并预热，这时常驻实例的私有工作集约 94 MB；如果不常驻，首次触发要 0.5 s 以上，而且用过一次后内存也会留在约 92 MB。所以选区遮罩改为原生绘制，见 ADR 0005；其余界面是否继续用 egui，见 ADR 0005 的 Consequences。

端到端延迟的定义：从 `SendInput` 注入热键前取的 QPC，到另一路 DXGI Desktop Duplication 第一次看到遮罩上的哨兵像素时那一帧的 `LastPresentTime`。“首次”指冷启动进程、空闲 2 s 后的第一次触发（每个配置 8 个样本）；“后续”指同一进程里接下来的 12 次触发（96 个样本）。内存在启动后空闲 2 s（首次触发前）和全部触发结束后空闲 2 s（用过后）各取一次，表中是 8 次冷启动的中位数。私有工作集就是任务管理器“内存”列显示的值。

- release 体积（`opt-level=3`、LTO、strip、`panic=abort`）：原生 0.21 MB（zip 后 0.11 MB），egui 6.77 MB（zip 后 3.13 MB），都远小于 15 MB。
- 进程启动到就绪（中位数）：原生常驻预热 209 ms，egui 常驻预热 627 ms。从零创建全部 GPU 资源：原生（D3D11 + Direct2D）约 0.10–0.13 s，egui（截屏用的 D3D11 + wgpu DX12 + egui 渲染器）约 0.47–0.51 s。
- egui 慢在冻结帧要先读回 CPU（4K 约 9 ms），再上传成 wgpu 纹理（约 11 ms）；原生方案直接在 GPU 上把截屏纹理交给 Direct2D（约 4.5 ms）。egui 首次触发后私有工作集增加约 29 MB，正好是一块 4K BGRA 帧的大小，推测是上传用的暂存内存没有归还。
- 常驻窗口复用时，有约 2–3% 的触发会先闪出上一次遮罩的画面，持续一帧（原生 2/104，egui 3/104）。Present 之后先 `DwmFlush` 再取消 cloak，可以消除这种闪烁（两者都是 0/104），代价是多等一帧。
- “egui · 全部按需”第二次及以后的触发，进程内的 Present 都成功了，但 DXGI 和 GDI 两种方式都没在屏幕上看到遮罩；没有深究，因为这个策略单看延迟就已经不可用。
- 两种方案都通过了拖拽框选验证：注入的拖拽得到的选区与预期一致，选区内像素与冻结前的桌面逐像素相同。

测量环境：AMD Ryzen 5 9600X、47 GB 内存、Windows 11 专业工作站版 build 26300、NVIDIA GeForce RTX 5070 Ti（驱动 32.0.16.1692）、单块 3840×2160@160 Hz 显示器，缩放 200%，测量时桌面为 SDR（复制出来的格式为 B8G8R8A8）。原型用 Rust 1.95、windows 0.62、egui / egui-wgpu 0.37、wgpu 30（只开 DX12 后端）、winit 0.30。多显示器混合缩放没有在真机上验证。原型代码、测量方法和原始数据见 `prototypes/overlay-latency/`。
